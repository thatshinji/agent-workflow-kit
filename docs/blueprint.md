# 通用 AI 协作开发工作流复刻方案 v0.1

> 提炼自一个真实在研项目的现行工作流（单人开发 + 多 AI agent 协作，App 与服务端并行推进，下称「参考项目」）：AGENTS.md（八步流程 + 铁律 + DoD）、REVIEW.md v1.4、TDD 协同规范 v1.0.0、后端契约草案清单、行为层测试用例归档体系（docs/test-cases/）、全栈编码规范、项目管理方案（docs/project-management/README.md）。
> 用途：在开发任何新 app（iOS / Android / Web / 小程序 / 服务端，任意语言）时复刻这套工作流。本文只写可移植的部分；原项目的业务内容（租户字段、设计工具、业务术语等）一律抽象为「槽位」，由新项目自己填。

---

## 0. 可行性结论

**可行。** 这套工作流的有效性不来自 Go、Swift 或某个具体工具，而来自一组平台无关的协作机制：谁拍板、谁写、谁审、证据怎么算数、知识往哪里沉淀。这些机制换成 Java/Node/Kotlin 全部成立，需要替换的只有最外层的工具名映射（第 4 章适配表）。

移植时分三层看：

| 层 | 内容 | 移植方式 |
|---|---|---|
| **内核**（第 1 章 12 个机制） | 角色、流程、证据制、用例库、门禁、沉淀 | 原样搬，不许改名改序 |
| **适配层**（第 4 章） | 测试框架、lint、契约格式、迁移工具 | 按技术栈查表替换 |
| **槽位**（第 5 章） | 本项目的铁律、failure 定义、★ 产品决策、强制失败分支 | 每个新项目开工时自填，填错比不填更糟 |

不成立的幻想先说清：这套流是为「一人（或小团队）+ 多个 AI agent 协作」设计的，纯人类团队或单人纯手写项目套用会过重；它的收益点（防 agent 顺着自己的实现补测试、防无证据 review 返工、防规范停留在口头）都是 AI 协作特有的病。

## 1. 内核：12 个平台无关机制

### 1.1 三角色 + 唯一合并键

- **决策者**（人）：只做判断题——批意图、批契约中的产品决策、批验收清单、点合并。不写代码、不填表。
- **Writer**（AI agent）：起草意图段、契约草案、场景清单与实现；负责把「待确认问题」列出来，不许自行发明需求。
- **Reviewer**（另一个 AI agent，最好与 writer 不同模型）：独立写测试或对抗性审计测试，按证据制 review，给裁决底稿。
- 原则：**决策串行、执行并行**；合并键永远在决策者手里，agent 不合任何 PR；调度者（如有）只拆任务、定接口、管流程，不进编码回路。

### 1.2 铁律层（仓库根 AGENTS.md）

每个仓库一份 agent 开工必读文件，含：项目速览、**铁律（违反即返工）**、目录/领域边界（哪个 agent 能碰哪些目录）、主流程、DoD、PR 规范。铁律分两类：

- **通用铁律**（直接搬）：不直推主干、一 issue 一分支、不碰密钥、不做破坏性操作、不私加依赖、未经批准不开工、无测试不提 PR、review 结论须经独立裁决。
- **项目铁律**（槽位，第 5 章）：本项目的不可违反项（如数据隔离维度、金额口径、禁止引入的重型组件）。

### 1.3 八步主流程

每个功能（一个 issue）严格按序，上一步没过不进下一步：

1. **意图与契约**：writer 起草意图段（给谁、解决什么）+ **非目标**与**不变行为**两栏草案，决策者拍板；涉服务端走契约草案流程（第 1.5 条）。
2. **场景清单与计划大纲**：场景清单先查用例库（增改或新建，行为层写法见 1.4）；计划大纲含改动范围、PR 拆分、**数据模型核对**（设计/需求出现的每个字段逐项对现行表结构，缺列先走提案）、受影响的已有测试。
3. **验收门**：清单 + 大纲经决策者批准才许写代码。决策者只验行为层事实与差异点，不验测试代码；高风险逐条过，低风险抽查。
4. **独立测试与冻结**：reviewer 按已批准清单独立写测试（或对抗审计），**先跑红留证**（跑不红的测试视为无效），然后冻结——writer 开发期不得改测试，改测试回第 3 步。用例清单另以人话发布到 issue，决策者确认后才开工。
5. **开发与自证**：writer 按 TDD 内循环实现（1.6）；自证材料齐备（测试全绿、一键门禁通过、视觉类附对比图）才许提 PR。
6. **Review**：reviewer 按 REVIEW.md 执行（1.8）；范围三样：场景覆盖、回归全绿、铁律合规。
7. **修复循环与裁决**：finding 走三态裁决（1.9）；轮次上限 3 轮，超限回方案层；收尾发布全量对账单（每条 finding 的裁决与修复证据）+ 一条决策者可一键执行的验真命令。
8. **合并与沉淀**：决策者合并；合并后强制归档四项（1.11）。

配套约束：WIP 限制（试水期 1 个、跑顺后最多 2 个）；单 PR 体量几百行内，超了按大纲拆成叠提 PR。

### 1.4 行为层用例库（跨端单一事实源）

- 归档对象是**功能的行为用例**，不是某个 PR 的测试记录：`docs/test-cases/` 一功能一文件（按业务域分子目录），四节固定——意图（意图/不变行为/非目标/历次变更）、行为用例（带稳定 ID，如 `AUTH-003`）、平台差异点、review 教训。
- **行为层措辞规范**：Given/When/Then 写业务事实，期望是业务结果；禁用实现词（点击/滑动/Toast/弹窗/组件名/路由/接口路径/UI 像素）。判据是**可映射性**：任一端的测试工程师只看用例就能写出该端测试，不需要猜。
- 例外三类：纯展示期望（一句业务期望 +「以设计稿为准」）、不可观察的内部行为（不写）、真正单端的行为（降级进平台差异点）。
- **INDEX 覆盖矩阵**：行 = 功能，列 = 该项目实际有的端（Web/iOS/Android/小程序/服务端），格 = 覆盖状态（✅ 已实现 / ⚠️ 部分 / ❌ 未实现 / — 不适用）。只登记已归档功能，逐行自然增长，不预填未来全集——INDEX 是事实台账，不是规划图。
- **活文档**：用例随功能演进在同一 PR 内同步更新现行版，不留历史版本；行为变了、文档没变 = review 的 Important。
- **新端走 Delta 模式**：第二个及以后的端消费同一用例库时，流程压缩为：意图只写相对归档用例的平台差异、验收门只验 delta、测试按用例 ID 1:1 挂号实现、合并后点亮 INDEX 对应列。

### 1.5 契约先行（服务端/跨端接口）

- writer 起草契约草案时逐项过《契约草案清单》，每项三选一标注：`已定方案` / `沿用规范`（注明出处） / `待确认问题`；reviewer 先查留白与一致性，有未交代项直接退回；决策者只批带 ★ 的产品决策项。
- 清单八组（内容通用，★ 项按项目调）：①接口（端点、校验、错误码、分页；★幂等）②数据模型（约束、索引、成对迁移、软删除、审计字段、数据量与归档）③业务规则（状态机、不变量、★计算口径、并发冲突、事务边界）④权限与安全（★授权矩阵、隔离维度只从登录态取、越权点清单、敏感数据只存 hash、防刷限流、★数据保留与真删）⑤外部依赖与异步（每个第三方本期真接还是桩、★桩的范围、失败策略、异步任务与补偿）⑥时间与边界（时区口径、边界值、★删除的关联语义）⑦客户端协同（可空性、错误码到用户提示的映射、变更影响面）⑧验收衔接（契约每条行为写成可测断言，喂给场景清单；桩行为逐项写明返回值）。
- 重要契约批准后进冻结区（版本提案制：改契约发新版文件 + 裁决记录，不直接改冻结版）；小契约在 issue 内批准即生效。
- 契约的机器形态：OpenAPI / Protobuf / JSON Schema 选一，全项目唯一事实源，客户端 DTO 由它对齐，漂移算 failure。


### 1.6 TDD 内循环（第 5 步内部的执行方法）

四步：**Step 0 规格映射 → Step 1 Red → Step 2 Green → Step 3 Refactor & Gate**，外加 reviewer 在 Step 4 独立复核。

- Step 0：把 issue 验收条件逐条映射成测试矩阵。每个功能点必须同时含正向用例与**强制失败分支**（按项目域调整，通用骨架：参数校验失败、未认证/认证失效、越权访问他人数据、限流与并发冲突、外部依赖失败时的降级行为）。
- Step 1：先写测试并运行确认红灯——测试若在功能未实现时不失败，视为无效测试。
- Step 2：只写让红灯变绿的最小实现，不顺手扩字段、不加未验证分支。
- Step 3：全绿保护下重构，过一键门禁后提 PR；PR 正文附 TDD 证据卡（红灯测试名 → 实现文件 → 门禁结果）。

配套一条防「后补测试偏差」的硬规矩：**验收条件必须与测试函数一一挂号**（测试名或注释带用例 ID），脱节即不合规。

### 1.7 隐藏场景

- reviewer 或决策者为每个功能保留 2–3 条隐藏场景，不下发 writer，只在终审轮运行；失败按最高严重度处理。
- 合并后由 reviewer 给出行为层底稿，writer 原样落盘入用例库（只整格式、不改语义）——隐藏性只存在于开发期，知识最终全量归档，不形成信息差沉淀。

### 1.8 Review 证据制（仓库根 REVIEW.md）

- **判据优先级链**（写死）：AGENTS.md 铁律 > 冻结契约与编码规范 > 决策者批准的场景清单 > TDD 规范 > REVIEW.md > 一般工程常识。冲突时按此链裁决，不吵架。
- **failure 按目录定义**：REVIEW.md 用一张表写清每个目录里「失败长什么样」（编译/测试失败、越权、迁移不可回滚、日志泄漏敏感信息、与契约漂移、文档把计划写成已实现……），reviewer 按表对号，不自由发挥。表的内容是槽位，结构照搬。
- **严重度三档**：Important（错误行为/安全/数据风险，必修）、Nit（不改变行为，每 PR ≤3 条不阻塞）、Pre-existing（标记转独立 issue，不算作者账）。
- **证据四件套**：每条 finding 必须给 `文件:行号` + 可执行 repro（或可引用的 spec 条款）+ `expected/actual` + `refute_hint`（什么结果能证明我错）。给不出复现标 `UNKNOWN`，不许写成 bug；不接受「可能 / 也许 / 最佳实践」式无证据表述。
- **审查范围纪律**：只审指定 commit 的 diff；第 2 轮起只看新 diff；跳过路径清单（生成物、锁文件、已裁决过的 finding、纯格式问题）；高风险路径（认证、会话、迁移、CI、密钥、冻结契约、破坏性脚本）单独安全审查 + 决策者确认。

### 1.9 裁决机制

- 每条 finding 由独立裁决判三态：`TRUE`（进修复队列）、`FALSE`（附反证关闭）、`UNKNOWN`（不得驱动返工、不得阻塞合并；安全/合规类走例外条款从严）。
- 修复收尾发布《全量问题裁决与修复对账单》：轮次、编号、严重度、位置、人话描述、裁决结论、修复 commit、验证证据，并附决策者一键验真命令。
- 争议超批准清单范围不在 agent 间来回，直接升级决策者。

### 1.10 机器检查优先

- 凡是能被机器判定的约定，必须落成机器检查（lint 规则 / 门禁脚本 / CI 步骤），文档口头约定只作为过渡。
- **规则等级即约束力**：关键规则必须 error 级——warn 的退出码是 0、CI 照绿、agent 权衡后会保留，等于没有。留 warn 只许用于纯提示类。
- **增量拦截、存量豁免**：新项目从零开始可全量拦截；往既有代码库引入时，只拦新增与改动行，存量随改动逐步清偿，避免一接入就全仓红灯逼出造假式修复。
- **一键门禁**：仓库提供统一入口（如 `make pr-check` 或等价脚本），串联格式化、lint、TDD 合规检查（生产代码与测试配对、反向断言存在性）、全量测试、迁移双向验证、构建；本地 100% 通过才许提 PR，CI 同口径复跑。
- 工具版本必须钉死，禁止 `@latest` 浮动依赖——CI 结果只应取决于仓库内容。

### 1.11 沉淀闭环（合并后归档四项）

每个功能 PR 合并后强制执行：① 隐藏场景解封落盘；② 本 PR 的行为用例增改落入功能文件现行版；③ review 教训蒸馏（一行一条：坑 + 处置）写入该功能文件的「review 教训」节（不设集中 lessons 文件，教训跟着功能走）；④ 更新 INDEX 覆盖矩阵。

**防腐规则**：同类 finding 第二次出现，必须落成机器检查或回归测试并开 issue 跟踪，不许靠 review 口头重复第三次。这是这套流能越用越轻的根本原因——每个坑只人工处理一次。

### 1.12 项目管理骨架

- **唯一任务池**：用代码托管平台的 Issue + 看板（如 GitHub Issues + Projects），不并行第二套任务系统。状态五态：需求池 → 待办 → 开发中 → 待验收 → 完成（+ 取消）；阻塞用标签写明原因与解除条件。
- **里程碑按退出条件定义**（「首版范围逐项通过」式），不按日期堆任务数；任务必填：结果、验收条件、来源、依赖、优先级、里程碑；任务粒度半天至两天，超了拆。
- **认领制**：一个 issue 同时只给一个 agent，开工前认领 + 留言；PR 用 `Refs #n` 关联，**禁用 Fixes/Closes 自动关单**——合并后进待验收，决策者人工核验后手动关单。
- **PR 规范**：标题与正文用团队工作语言、写清改动点与验证证据、风险自评（Low/Medium/High，决定决策者合并前细看程度）、修复了 review 问题的列 finding 编号与裁决结果。
- **DoD**：合并 ≠ 完成；满足验收条件 + 证据齐备 + 决策者确认用户结果，才算完成。

## 2. 通用落地蓝图：新项目从 0 到 1 的五阶段

### 阶段 A：仓库骨架（第 1 天）

- 建仓 + 目录结构（单仓多端 monorepo 或按端分仓均可；分仓时每仓各备一份 AGENTS.md，契约与用例库放共享仓）。
- 定下：任务池与看板、分支命名 `<agent>/<issue号>-简述`、PR 模板（含风险自评与证据栏）、里程碑骨架（按退出条件）。
- 填第一版槽位（第 5 章）：项目铁律、目录边界、高风险路径清单。

### 阶段 B：文档集落地（第 1–2 天）

按第 3 章清单把 10 份文档的「结构」建起来，内容先写最小版（能跑通第一个功能为准），不追求一次写全——这套文档集本身是活文档，靠后续每个 PR 的教训迭代。

### 阶段 C：门禁接电（第 2–3 天）

- 按第 4 章适配表选工具链，提交各端 lint/format 配置与 CI；统一一键门禁入口跑通（空仓也要先绿）。
- 实现 TDD 合规检查脚本（ diff 分析：生产改动须配对测试改动、测试须含反向断言关键词）——逻辑与语言无关，参考实现是零依赖 Python，可直接改路径规则复用。

### 阶段 D：第一个功能全程试跑（第 1 周）

选一条最小但完整的真实闭环功能，严格走完八步一遍（含隐藏场景与归档四项）。目的不是交付功能，是把流程的每处摩擦暴露出来：清单粒度、门禁耗时、review 往返。试跑中的所有别扭当场修文档，不攒。

### 阶段 E：固化与裁剪（试跑后）

- 决策者过一遍：哪些门禁是真拦住过问题的（留）、哪些只是仪式（删或降级）；把试跑教训写进各文档的变更记录。
- 团队规模或端数量变化时，回第 6 章调整档位。

## 4. 按端与按语言适配表（适配层）

内核机制不变，只换下表中的工具对应物。原则：每语言选**该生态的主流默认**，不猎奇；版本钉死；配置进仓。

### 4.1 客户端

| 维度 | iOS（Swift） | Android（Kotlin） | Web（TS/React 等） | 跨端（Flutter/RN 等） |
|---|---|---|---|---|
| 测试框架（按用例 ID 挂号） | XCTest / swift-testing | JUnit 5 + Espresso（UI） | Vitest / Jest + Testing Library | flutter_test / Jest |

| 设计源约束 | 设计稿工具导出 + 设计 token 文件 | 同左 | 同左；机器生成物目录只读不手改 | 同左 |
| Delta 消费要点 | 权限/系统组件差异写平台差异点 | 权限/后台限制差异同理 | 浏览器/SEO 差异同理 | 双端差异分别成列 |

### 4.2 服务端

| 维度 | Go | Java | Node.js（TS） | Python |
|---|---|---|---|---|
| 测试框架 | go test（表驱动） | JUnit 5 + Testcontainers | Vitest / Jest + supertest | pytest |

### 4.3 跨栈通用对应物

- **门禁脚本**：任何语言可写，参考实现用的是零依赖 Python + `git diff` 分析——「生产改动↔测试配对」「反向断言关键词」两条规则与语言无关，只需按栈改文件后缀与目录模式。
- **覆盖矩阵的列** = 项目端集合，增减端只改 INDEX 表头与 playbook，不动机制。
- **错误包络**：全项目统一一种错误结构（码 + 人话 message），错误码到用户提示的映射归客户端，属契约的一部分。

## 5. 每项目必自填的槽位（开工清单）

以下槽位填错或留空，工作流会空转或误伤，第一个功能开工前必须由决策者填完：

1. **数据隔离维度**：多租户/多组织/单用户？隔离字段是什么、只从哪取（登录态）、越权点怎么枚举。（如 SaaS 是 tenant_id、协作类产品是 workspace_id；单机工具可能没有——没有就把「强制失败分支」里的越权项换成本项目的高危项，如本地数据损坏恢复。）
2. **项目铁律 3–6 条**：本项目不可违反的业务/技术不变量（如金额整数分、统计数走确定性计算不经模型、禁止的架构件）。
3. **failure 定义表**：按目录逐行写「失败长什么样」，必须含：契约漂移、敏感信息落日志、迁移不可回滚、文档失真四类通用项 + 本项目特有项。
4. **高风险路径清单**：哪些路径走逐条验收 + 单独安全审查（通用起点：认证、会话、支付、数据迁移、删数据、CI 与密钥）。
5. **契约清单的 ★ 项**：幂等、授权矩阵、计算口径、数据保留与真删、删除关联语义、桩的范围——逐项给出本项目的默认答案或留待逐功能拍板。
6. **强制失败分支表**：按本项目域增删（如 IoT 加断线重连、内容产品加审核失败、电商加库存不足与重复下单）。
7. **设计源**：设计稿从哪来、怎么与代码 1:1 对账（有设计工具用导出包 + manifest；没有就用「原型图/截图 + 页面清单」的轻量形态，但「唯一设计源、不凭空造页」不许取消）。
8. **风险分级口径**：Low/Medium/High 的划分标准（决定验收与合并的细看程度）。

## 6. 裁剪档位（按项目规模选）

| 档位 | 适用 | 启用机制 |
|---|---|---|
| **最小版** | 原型验证期、单端、1 人 + 1 agent | 1.1 角色（可 writer/reviewer 同 agent 不同会话，但合并键在人）、1.2 铁律、八步简化为「意图→清单→验收→实现→review→沉淀」、1.4 用例库、1.8 证据制、1.10 机器门禁、1.11 沉淀。暂缓：隐藏场景、Delta、对账单（一句话裁决记录代替） |
| **标准版**（参考项目现行） | 正式产品、多端或计划多端、有服务端 | 12 个机制全量 |
| **加强版** | 涉支付/医疗/强合规、多人协作 | 标准版 + 双 reviewer 并行交叉仲裁、高风险路径双人确认、台账审计、发布门禁与回滚演练 |

裁剪原则：可以暂缓机制，但不许降级机制内的标准（如用了证据制就不许无证据 finding；用了用例库就不许写实现词）。

## 7. 反模式清单（实战教训，移植时直接写进新项目 AGENTS.md 的注意事项）

1. **采信执行方的「已核查」而不自验**：报告只给结论不给原文时，关键文件必须自己回读行数/锚点再采信。教训是真金白银换来的。
2. **warn 级规则长期挂着**：等于没有规则，且污染日志掩盖真警告。要么 error，要么删。
3. **文档声称与实际落地不一致**：规范里写「已接入 CI」而实际没接——文档即契约，声称必须可验证；拿不准就如实写「暂未接入」。
4. **规范只写文档不接电**：没有 lint 配置与 CI 步骤的规范，三个月后必然被遗忘。
5. **后补测试偏差**：顺着实现补测试必漏契约边界与失败分支——测试先行 + 独立作者 + 跑红留证三件缺一不可。
6. **review 无限轮次**：3 轮上限，超限回方案层；同类问题按 class 一次说清。
7. **决策者被拉去填表**：意图、草案、清单都由 writer 起草，决策者只做判断题；要决策者填空的流程活不过两周。
8. **一次性大爆炸指令**：给 agent 的任务一次一件事、边界写死；大而全的指令必然被误解（设计与编码同理）。
9. **把计划写成已实现**：文档与对账中最常见的失真，review 时按 failure 处理。
