# 快速开始 — 约 30 分钟把这套工作流装进你的项目

[English](quickstart.md) | 简体中文

本指南把一个新仓库从零带到「可以按这套流程开工第一个功能」。原理讲解在[蓝图](blueprint.md)里，每一步的产物长什么样在[完整示例](../examples/invite-code/)里，本页只给路线。

## 适合谁

- 用一个或多个 AI 编程 agent 写代码的单人开发者和小团队。
- 任意技术栈：原生移动端、Web、任意语言的服务端。
- 不适合：完全不用 agent 的纯人类团队（但仍可单独借用其中几个机制，比如证据制 review）；以及写完即弃的原型。

**前置条件**：一个 git 仓库（GitHub/GitLab 等）、一位担任决策者的人、至少一个 AI 编程 agent（需要两个角色，两个工具或两个会话都可以）、想用门禁脚本的话需要 Python 3。

## 第 0 步 — 一行命令装好（1 分钟）

在**你的**仓库根目录运行：

```bash
curl -fsSL https://raw.githubusercontent.com/thatshinji/agent-workflow-kit/v0.3.2/scripts/install.py | python3 -
```

脚本会把 kit（v0.3.2 版）下载到临时目录，再把全部模板（对照表如下）、门禁脚本和它的配置一键铺进你的仓库。已存在的文件绝不覆盖——冲突项跳过并报告（`--force` 才覆盖）。只想预览计划就在 `python3 -` 后加 `--dry-run`；要中文模板加 `--lang zh-CN`（落地时用无后缀名，你的仓库保持单语）；要某个技术栈的 lint 起步配置加 `--stack go`（或 `web` / `swift` / `python`）；想装其他版本用 `--kit-version <标签>`，装最新版用 `--kit-version latest`。

不想管道执行远程脚本？把本仓库 clone 下来，运行 `python3 /path/to/agent-workflow-kit/scripts/install.py`，效果相同。手动拷贝也可以，对照表就是这张：

| kit 里的文件 | 你仓库里的位置 |
|---|---|
| `templates/AGENTS.md` | `AGENTS.md`（根目录） |
| `templates/REVIEW.md` | `REVIEW.md`（根目录） |
| `templates/test-cases/*` | `docs/test-cases/` |
| `templates/project-management/*` | `docs/project-management/`（`platform-playbook.md` 按端改名） |
| `templates/specs/coding-standards.md` | `docs/tech-specs/coding-standards.md` |
| `scripts/check_tdd_compliance.py` | `scripts/` |
| `scripts/tdd-check.config.example.json` | `tdd-check.config.json`（根目录） |

## 第 1 步 — 填 8 个槽位（15 分钟 – 半天）

这是唯一需要真正动脑的一步，其余都是机械操作。每个槽位都标了落点：

1. **数据隔离维度** — 多租户？多工作区？单用户？把规则写进 `AGENTS.md` 铁律（如「所有查询必须携带 `tenant_id`，且只从登录态取」）。如果你的应用没有共享数据，就把这个槽位换成你项目风险最高的不变量。
2. **项目铁律（3–6 条）** — 你的不可协商项（金额一律整数分、禁用重型 ORM、统计数字由代码确定性计算不经模型……）→ `AGENTS.md`。
3. **failure 定义表** — 按你的目录重写 `REVIEW.md` 第 2 节的表；四个通用行务必保留：契约漂移、敏感信息落日志、迁移不可回滚、文档把计划写成已实现。
4. **高风险路径** — 认证 / 会话 / 支付 / 数据迁移 / 删数据……列入 `AGENTS.md` 与 `REVIEW.md` 第 8 节。
5. **契约的 ★ 决策** — 幂等、授权矩阵、计算口径、数据保留与真删、删除关联语义、桩的范围，逐项给出默认答案 → `contract-checklist.md`（也可以留到逐功能拍板，但要写明）。
6. **强制失败分支** — 按你的领域调整 TDD 规范里的清单（IoT 加断线重连、电商加库存不足与重复下单……）。
7. **设计源** — 设计稿从哪来、代码怎么与它 1:1 对账（设计工具导出包 + 清单，或至少页面清单 + 截图）。「唯一设计源、不凭空造页」这一条不能省。
8. **风险分级口径** — Low/Medium/High 在你的项目里怎么划分（它决定各道门的严格程度）→ `AGENTS.md` 的 DoD / PR 模板。

## 第 2 步 — 接门禁（5 分钟）

安装脚本已经把 `scripts/check_tdd_compliance.py` 和 `tdd-check.config.json` 放进你的仓库了。按你的目录结构修改配置里的路径规则（示例里有 Go / Web / Swift / Java 四种现成样例），再照 [scripts/README.md](../scripts/README.md) 把它挂进你的一键门禁和 CI。在未改动的代码树上先跑一次：必须输出 `PASS`。

## 第 3 步 — 定角色（2 分钟）

把谁是谁写进你的 `AGENTS.md`：

- **决策者**：你本人（或你的负责人）。批意图、批 ★ 决策、批验收清单；唯一能点合并的人。
- **Writer（写作者）**：agent/工具 A。起草意图、契约、清单；负责实现。
- **Reviewer（审查者）**：agent/工具 B——尽量用**不同的模型**；实在没有，就用同一个工具开一个不带实现上下文的新会话。独立写测试、按证据制 review。

## 第 4 步 — 跑第一个功能（真正的试炼）

挑一个最小但完整跨界的功能（比如 UI → API → 数据这一整条线），严格按 `AGENTS.md` 的八步走一遍，全程把 [examples/invite-code/](../examples/invite-code/) 打开放在旁边——你要产出的每样东西（意图段、行为清单、红灯证据、对账单、归档状态）在那里都有一份成品样本。

别扭是必然的，这正是试跑的目的：跑完后把每个别扭**修进文档**（蓝图落地五阶段的最后一步），而不是记在脑子里。

## 第 5 步 — 第一次合并之后

- 归档四项都做了吗（隐藏场景解封、用例更新、教训蒸馏、覆盖矩阵加行）——漏了就现在补，并记下为什么当时会被漏掉。
- 更新你的 `docs/test-cases/INDEX.md`：第一行真实记录诞生，用例库活了。
- 以后加新端时走 Delta 模式消费同一份用例库（见平台 playbook 模板），永远不需要重跑第 1–4 步。

## 轻量路径：最小版

如果现阶段觉得全量太重，先上五个机制——`AGENTS.md` 铁律 + 压缩版流程、行为用例库、证据制 review、机器门禁、归档沉淀，其余（隐藏场景、Delta、对账单全文）随规模后补。但有一条底线：**已采用的机制不许降级**——没有证据的证据制、写满实现词的行为用例，比不采用还糟。

## 诚实的时间预期

| 阶段 | 典型耗时 |
|---|---|
| 第 0–3 步（搭建） | 机械操作约 30 分钟 + 填槽位 15 分钟 – 半天 |
| 第一个功能试跑 | 第一周内完成；按功能正常工时 × 1.5 预留 |
| 开始回本 | 从第二个功能起：review 轮次变少、决策不再重复争论、测试开始真正算数 |

## 常见问题

- **只有一个 agent 怎么办？** 同一个 agent 开两个会话：一个当 writer，另一个只给清单和设计稿、当 reviewer。重要的是上下文独立，其次才是厂商不同。
- **已有大量存量代码怎么办？** 门禁天生只拦增量（新增与改动行）；用例库随功能逐个功能长。永远不要一次性改造全仓。
- **没有服务端/API 怎么办？** 纯客户端工作可以跳过契约清单，其余保留；哪天出现两个组件需要就数据达成一致，清单自然回归。
