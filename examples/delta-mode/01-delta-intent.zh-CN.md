# 步骤 1 产物（Delta 形态）—— Issue #118：移动 App 中的邀请码加入

## 意图（Writer 起草，决策者批准）

Web 上线六周后，凭邀请码加入来到移动 App。在 Delta 模式下，意图不复述功能本身——只说明本平台继承什么、在哪里不同。功能的行为已在 issue #101 中决定，存放在 `docs/test-cases/workspace/invite-code.md`；本文档永远不覆盖它。

### 继承——不重新决策、不重新评审

- **服务端契约，不变**：`POST /workspaces/join { code }`，配标准错误封装（`INVITE_NOT_FOUND`、`INVITE_EXPIRED`、`INVITE_EXHAUSTED`、`ALREADY_MEMBER`、`RATE_LIMITED`）。App 是同一个接口的新客户端；不写契约草案。
- **业务规则，不变**：6 位码；重复加入返回 `ALREADY_MEMBER` 且不消耗次数；失败尝试按每人每小时 10 次限流；码有效期 7 天、共 5 次使用次数；重新生成立即使旧码失效。
- **既有行为，不变**：成员列表邀请照旧；加入只授予标准成员角色；重新生成不影响已有成员。

### 平台差异（仅本平台）

- **码从 App 外部进来**：邀请链接经深链直接打开加入页，码也可以在 App 内扫码录入。没有「找到加入表单」这一步。
- **App 只消费码，从不生成码。** 建码与重新生成留在 Web（所有者流程不变）。App 没有所有者侧的码管理。
- **粘贴在客户端做规范化**：粘贴的文本在提交前先去首尾空白、去掉内部空格，把 INV-008 的输入规范化扩展到码在移动端真实的到达方式（从消息里复制、带空格）。
- **离线要明说，绝不静默**：没有连接时，App 明说加入需要连接，且不发送任何东西。加入操作永不排队等待日后静默重试。
- **★ 未登录时点开深链**——带码链接被未登录的人点开：丢弃这个码，还是保留？→ *决策者：保留——登录后，加入流程恢复，码已预填。* `decided by decision-maker`

### 非目标（本平台）

- App 内不做建码、重新生成与用量展示（只在 Web，如 #101 所定）。
- 不新增错误码、不做客户端限流——计数留在服务端。

**验收门记录**：决策者批准了差异清单和那条新的 ★ 决策。按 Delta 操作规程，已归档的行为未再提交重批。步骤 2′（用例映射）可以开始。
