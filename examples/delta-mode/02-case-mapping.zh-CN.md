# 步骤 2′–3′ 产物（Delta 形态）——用例映射：已归档 INV 用例 → 移动端

> 由 Writer 依据已归档的用例文件（`docs/test-cases/workspace/invite-code.md`）和已批准的 Delta 意图（01）写成。每个已归档用例都有处置结论；没有一条被静默丢弃。移动端测试按这些 ID 1:1 实现，照例先跑红。

## 已归档用例的处置

| 用例 | 处置 | 在移动端的含义 |
|---|---|---|
| INV-001 有效码加入 | 原样复用 | 加入本身是服务端用例；移动端测试只验客户端结果——成员资格的成功状态被呈现出来。 |
| INV-002 过期码被拒 | 原样复用 | 过期由服务端强制；移动端测试验证过期结果以已过期的形态呈现。 |
| INV-003 用尽的码被拒 | 原样复用 | 与 INV-002 相同，针对用尽结果。 |
| INV-004 未知码不泄露任何信息 | 原样复用 | 移动端测试验证通用的无效码结果被呈现，且不渲染任何工作区信息。 |
| INV-005 防止重复加入 | 原样复用 | 移动端测试验证「已是成员」结果被呈现；「不消耗次数」仍由服务端测试套件断言。 |
| INV-006 猜测触发限流 | 服务端专属——移动端不复测 | 计数与强制都在服务端（见 INV-H1 的教训）。客户端只通过标准错误映射渲染共用的 `RATE_LIMITED` 结果；在移动端重复计数测试等于把服务端测两遍。 |
| INV-007 重新生成使旧码失效 | 服务端专属——移动端不复测 | App 没有重新生成的界面；失效发生在服务端。旧码在 App 里提交时呈现为 INV-004 的通用结果，上文已覆盖。 |
| INV-008 输入规范化 | **适配** | 行为不变——加入成功——但机制变了：客户端在提交*之前*规范化粘贴的输入（去首尾空白、转大写、去掉内部空格），按 Delta 意图。服务端用例依然成立；移动端测试断言发出去的就是规范化后的值。 |
| INV-H1 畸形尝试同样计入限流 | 服务端专属——移动端不复测 | 纯服务端的计数性质。客户端规范化已挡住大多数畸形提交，但计数仍由服务端强制、由服务端测试。 |
| INV-H2 限流按人计 | 服务端专属——移动端不复测 | 这是服务端的跨用户隔离性质；单设备客户端没法同时摆出两个用户的计数器。由同一次验收门中的服务端测试套件覆盖。 |

## 新增平台用例

- **MOB-001 深链打开加入页**——Given 有效的邀请链接，When 装有 App 的用户打开它，Then 加入页打开且码已预填，可直接确认。
- **MOB-002 粘贴规范化**——Given 粘贴的码带首尾与内部空格，When 用户提交，Then 发出的是规范化后的码，加入成功。
- **MOB-003 离线要明说**——Given 设备没有连接，When 用户尝试加入，Then App 明说加入需要连接且不发送任何东西；没有加入操作被排队或静默重试。

还有一条场景按标准规则由 Reviewer 保管为**隐藏场景**，到评审轮次才解封：

- **MOB-H1 经深链打开自己的码**——Given 深链带的码属于用户已经加入的工作区，When 已登录用户打开它，Then 他们落到「已是成员」结果（INV-005）——不是报错——且不消耗次数。

**验收门记录**：决策者批准了这份映射和三条新用例（MOB-H1 在评审时解封）。验收门只验 Delta 本身——已归档用例没有被重新批准。可以开始实现。
