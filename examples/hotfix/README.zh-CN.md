# 示例：紧急修复通道——生产 bug，压缩但不跳过

`templates/AGENTS.md` 里的八步流程是按功能规模设计的。生产事故等不起完整周期——但"紧急"恰恰是团队最容易跳过那些本能拦住*下一个*事故的步骤的时候。紧急修复通道就是流程给出的答案：**同样的步骤，在压缩安全的地方压缩，在不安全的地方全强度保留。**

**它是什么**：一个先写成跑红的回归测试、一轮带裁决的完整评审、以及和任何功能一样的归档回写——围着一个刻意做小的修复。

**它不是什么**：它不是跳过通道。什么都不豁免。意图、验收门、清单、评审都照常发生；它们只是缩到事故的尺寸，而不是消失。

**本次事故**：在[邀请码功能](../invite-code/README.zh-CN.md)（issue #101，已上线）里，过期的邀请码返回 `INVITE_NOT_FOUND` 而不是 `INVITE_EXPIRED`。用户分不清"这个码过期了"和"这个码根本不存在"——支持人员也分不清。本走查在不改动任何一条业务规则的前提下修复这个 bug（issue #137）。

**角色阵容**：不变——决策者（人类）· Writer（agent A）· Reviewer（agent B，不同模型）。

## 什么时候可以用紧急修复通道

三个条件必须同时成立；任何一条不成立，工作就走完整流程：

1. **生产影响真实且正在发生**——用户现在就在撞上这个 bug，而不是"将来可能"。
2. **改动半径小**——修复局限在一处已知位置；不改业务规则、不改数据模型、不改契约决策。
3. **决策者批准走快速通道**——明确批准、写在 issue 里、工作开始之前。
