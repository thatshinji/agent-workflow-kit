# 第 1 步产物 — Issue #101：用邀请码加入工作区

## 意图（Writer 起草，决策者批准）

目前，工作区所有者只能在成员列表里逐个邀请成员；当整个团队或整个班级需要一次性加入时，这种方式就行不通了。本功能让所有者生成一个简短的邀请码，通过任意渠道分享出去；任何拿到邀请码的人，一步就能加入工作区。

### 不变行为（Writer 提议 — 已批准）

- 成员列表邀请保持原样，照常工作。
- 只有所有者能查看或管理工作区设置；加入只授予标准成员角色，别无其他。
- 已有成员不受邀请码重新生成的影响。

### 非目标（Writer 提议 — 已批准）

- 本轮不做一人一链接的专属邀请链接。
- 不做审批队列：邀请码有效即立即加入。
- 不做邀请码使用数据页面（次数只存储，不展示）。

## 契约草案（Writer 起草，逐项过契约清单）

每一项标注 `decided` / `follows standard` / `open question` 三者之一：

- **接口** — `POST /workspaces/join { code }` → `200 { workspace_id }`。错误使用标准错误包络：`INVITE_NOT_FOUND`（404）、`INVITE_EXPIRED`（410）、`INVITE_EXHAUSTED`（409）、`ALREADY_MEMBER`（409）、`RATE_LIMITED`（429）。`decided`
- **数据模型** — 每个工作区只有一个有效邀请码；邀请码一行数据包含 `code`（唯一）、`workspace_id`、`expires_at`、`max_uses`、`uses`、`revoked_at`。重新生成时把上一行置为已吊销，而不是删除（留审计痕迹）。`decided`
- **业务规则** — 邀请码为 6 个字符，取自不含易混淆字形的大写字母数字字符集（没有 `0/O`、`1/I`）；查找前先把输入规范化（去首尾空格 + 转大写）。`decided`
- **★ 幂等** — 用同一个邀请码加入两次，不得重复计算一次使用次数，也不得产生重复成员关系。→ *决策者：第二次加入返回 `ALREADY_MEMBER`，且不消耗使用次数。* `decided by decision-maker`
- **授权与安全** — 不存在的、已吊销的、格式错误的邀请码，一律返回同一个通用的 `INVITE_NOT_FOUND`；加入成功之前，响应里绝不包含工作区名称。失败尝试按用户限流。`decided`
- **★ 限流参数** — 允许多少次失败尝试、窗口多长？→ *决策者：每用户每小时 10 次失败尝试，超过后即使提交正确的邀请码也返回 `RATE_LIMITED`。* `decided by decision-maker`
- **★ 邀请码有效期与使用次数** — 默认值？→ *决策者：7 天、5 次；所有者可随时重新生成，重新生成后旧码立即失效。* `decided by decision-maker`
- **外部依赖** — 本轮没有（分享发生在应用之外）。`decided`
- **验收衔接** — 上述断言原样喂给第 2 步的行为清单。桩分组：无——没有任何外部依赖要打桩。

**验收门记录**：决策者已批准意图、两份清单（不变行为与非目标）和三项 ★ 决策。第 2 步可以开始。
