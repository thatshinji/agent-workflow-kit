> 建立日期：<YYYY-MM-DD>。修改本文件需经决策者批准。

## 项目概览

- **<项目名>**：<一句话——它是什么，其核心循环或价值主张是什么>。
- **架构**：<例如 monorepo：`apps/` 客户端 + `server/` 后端 / 或你的目录布局>。

## 铁律（hard rules，违反任一条都要返工）

1. **禁止直推主分支。** 一切经由 PR 落地；只有决策者可以合并（merge）。
2. **一 issue 一分支（one issue per branch）。** 分支名：`<agent>/<issue-number>-<short-description>`。
3. **禁止就地修改已冻结（frozen）的规格。** 用版本化提案演进。
4. **绝不碰密钥。** 不读、不写 `.env`、密钥、令牌或密码。任务需要凭据时，向决策者索取。
5. **禁止破坏性操作。** 不删除迁移历史、不强推、不修改其他 agent 的分支。
6. **未经批准不得引入新依赖或重型架构。** 新依赖必须先在 issue 里说明理由并获批。<项目槽位：点名本项目禁止的重型组件，例如重型 ORM、消息队列、过早的微服务拆分。>
7. **验收门通过前不许写代码。** 意图、契约、行为清单必须先获批（流程第 3 步），才可以开始实现。没有测试不许提 PR；每个新测试套件必须包含反向/边界用例（见 TDD 规格）。
8. **审查 finding 必须经过裁决（adjudication）。** finding 只有经独立裁决标为 `TRUE`（附可复现的证据（evidence））后，才进入修复队列。无法核实的意见（`UNKNOWN`）永远不阻塞合并。Reviewer 必须先读 `REVIEW.md`；评审最多 3 轮。
9. <项目槽位：你的数据隔离规则 —— 例如「所有租户（tenant）数据的查询/写入都必须携带 `<tenant_id>`，且取自已认证的会话，绝不取自客户端输入。」（租户隔离，tenant isolation）>
10. <项目槽位：再写 0–3 条项目不变量，例如金额一律用整数分；统计由确定性代码计算，绝不由 LLM 生成。>

## 八步流程（每个功能 / issue 走一遍）

上一步未通过，下一步不开工。

1. **意图与契约。** 决策者给出设计/需求。Writer 起草*意图段*（服务谁、解决什么）以及拟议的**非目标**与**不变行为**，交决策者批准 —— 这一对内容未获批，不许开工。后端工作还要起草契约：逐条过契约清单（contract checklist），每条标 `decided` / `follows standard <ref>` / `open question`。带 ★ 的条目是产品决策：Writer 绝不自作主张，全部上交决策者。重要契约走规格提案流程冻结；小契约在 issue 内获批即生效。Writer 绝不臆造需求 —— 无法从已有材料推导出来的，一律记为开放问题。
2. **行为清单与计划大纲。** (a) 清单：先查 `docs/test-cases/` —— 扩展已有文件，或从模板新建。用例写在**行为层**（behavior layer，平台无关的 Given/When/Then → 业务结果；不许出现实现词 —— 见行为用例模板说明）。平台特有的交互写进*平台差异*一节。每条用例都要标注来源（设计屏 / 契约条款 / 铁律）。依赖桩的行为拆成两组：*桩行为*（本轮接受）与*真实行为*（联调时激活；不冻结为契约）。(b) 计划大纲：要改的文件、PR 拆分、**数据模型核对**（设计里的每个字段都与现行 schema 核对；缺列先走规格提案）、受影响的已有测试清单。
3. **验收门。** 清单 + 大纲必须经决策者批准后才许写代码。决策者只核对行为事实与差异，不审测试代码。高风险工作（认证、会话、迁移、支付、数据删除）逐行看；低风险可抽查。
4. **独立测试并冻结。** 测试代码由 Reviewer 依据已批准的清单编写（若 Writer 写了测试，则由 Reviewer 做对抗性审计）—— Reviewer 只看设计与清单，绝不参考 Writer 的实现思路。测试必须先提交、**先跑红（red），并把失败输出留作证据**（跑不红的测试是无效的），然后**冻结**：实现期间 Writer 不得修改；要改测试，回到第 3 步重批。Reviewer/决策者保管 2–3 条**隐藏场景**（hidden scenarios），到最后一轮评审才解封（unseal）。冻结后，清单还要以人话发到 issue，决策者确认后才进入第 5 步。
5. **实现与自证。** Writer 按 TDD 循环实现（见 TDD 规格）。提 PR 的条件：全部已批准测试跑绿（green）、一键门禁（`<make pr-check>`）通过、涉及 UI 的要附与设计源的并排截图。
6. **评审。** Reviewer 按 `REVIEW.md` 工作。评审范围只有三样：清单覆盖率、回归套件是否全绿、铁律合规。严重度（severity）、证据、轮次规则都在 `REVIEW.md` 与评审协议里 —— 不在这里重复。
7. **修复循环与对账。** 按裁决协议走。超出已批准清单的争议直接上交决策者，不在 agent 之间来回扯皮。修复完成后，把完整的**对账单**（reconciliation statement）发到 issue：每条 finding 的轮次、严重度、位置、人话描述、裁决结论、修复提交与验证证据 —— 外加一条决策者复制粘贴即可运行的验真命令，几秒内就能核对结论。
8. **合并与归档。** 决策者合并（高风险路径合并前要亲自读关键 diff）。合并后四项归档动作强制执行：① 隐藏场景从 Reviewer 的行为层底稿中解封，逐字写进 `docs/test-cases/`；② 本 PR 的行为用例变更落进该功能文件的现行版本；③ 评审教训提炼（每条一行：坑 + 解法）进该功能文件的*评审教训*一节；④ 更新 `docs/test-cases/INDEX.md` 的覆盖矩阵（coverage matrix）。**同类 finding 第二次出现时，必须落成机器检查（machine checks，CI/lint/门禁脚本规则）或回归测试，并开 issue 跟踪 —— 绝不搞第三轮口头提醒。**

**追加平台（Delta 模式）。** 当第二个（或更晚的）平台实现一个行为用例已归档的功能时，流程压缩：意图只写相对于已归档用例的平台差异；验收门只验 delta；测试按已归档用例 ID 逐条 1:1 实现；合并后更新覆盖矩阵中新平台的那一列。见平台实战手册（playbook）模板。

PR 体量预算：几百行。更大的工作按计划大纲拆成叠放的 PR。

## 完成定义（Definition of Done）

1. **认领**：在 issue 下评论 + 自行 assign；把看板卡片移到 In Progress。WIP 上限：<工作流还不熟时为 1，跑顺后至多 2>。
2. **先读**：`docs/project-management/README.md`、TDD 规格与相关契约。跨端工作以 API 契约为准。
3. **计划**：功能开发走八步流程。复杂的非功能工作先提交计划获批。
4. **门禁**（提 PR 前全部通过）：
   - TDD 合规：生产代码变更必须在同域配齐测试；新测试包含反向/边界断言（`<make tdd-check>`）。
   - <后端槽位：测试数据库与全量测试命令，例如 `go test -race ./...` 100% 全绿。>
   - <客户端槽位：设计源合规检查，例如页面必须与设计导出 1:1 对应并登记进 manifest（`<make design-check>`）。>
   - 数据库变更以成对的 up/down 迁移交付，并验证可干净回滚（`<make migrate-verify>`）。
   - 一键门禁 `<make pr-check>` 本地 100% 通过。
5. **PR 约定**：
   - 用<团队的工作语言>书写；标准技术术语可保留英文。
   - **绝不**使用自动关单关键词（`Fixes #`、`Closes #`）。一律用 `Refs #<issue>`。
   - 写明改了什么、验证命令及其输出证据。
   - 附带风险自评（Low / Medium / High）—— 它决定决策者合并前读得多细。
   - 若 PR 修复了审查 finding，逐条列出 finding ID（`R-YYYYMMDD-NNN`）及其裁决结论（`TRUE`/`FALSE`/`UNKNOWN`）与证据。
   - issue 的验收勾选项逐项核对后打勾。
   - 合并后 issue 转为「待验收」；决策者核验后手动关单。
6. **归档**：在 issue 上记录 agent 会话链接、分支与 PR 链接。AI 永远不是最终验收人。

## 代码约定（摘要 —— 全文见编码规范）

- 注释解释*为什么*，用人话写，非专业人士也能看懂。
- <槽位：分层规则，例如「业务代码绝不直接写裸 SQL；数据访问统一走 repository 层。」>
- <槽位：错误规则，例如「上游错误要转译成人话消息；原始堆栈绝不透给客户端。」>
- <槽位：日志规则，例如「手机号、验证码、令牌、密码绝不写进日志；手机号要脱敏。」>
