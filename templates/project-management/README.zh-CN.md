# <Project Name> — 项目管理

建立于：<YYYY-MM-DD>。范围：<谁来运行这个项目，如一名决策者 + AI agents>。本文档只定义管理方式；不决定产品范围，也不声称任何事项已实现或已验收。

## 工具

使用代码托管平台自带的 Issues + Milestones + Projects 作为单一任务池。不要并行运行第二套任务系统。<如你的托管平台不同可调整——规则是"恰好一个池"，不是品牌。>

## 里程碑（按退出标准定义，不按日期）

| 里程碑 | 退出标准 |
|---|---|
| M0 · 基线 | 范围来源已冻结、可用工时已知、现有资产已盘点、第一条验收流程已写出 |
| M1 · 第一条真实闭环 | 选定的端到端流程在真实设备/服务上跑通，并有验收证据 |
| M2 · v1 范围完成 | M0 确认的 v1 清单中每一项均通过；延后项有明确的变更记录 |
| M3 · 封闭测试 | 安全、隐私、恢复与分发条件满足；测试反馈闭环已关闭 |
| M4 · 首次公开发布 | 发布清单通过；监控与事故责任人明确 |

M0 之后才估算日期；记录前几轮的实际投入，用证据修正计划。

## 看板与任务纪律

- 状态：储备池 → 待办 → 进行中 → 待验收 → 已完成（外加已取消）。阻塞项用标签标注，并写明原因与解除条件。
- WIP：工作流尚新时，进行中最多 **1** 项；跑顺后最多 **2** 项。待验收同样设上限（≤2）——先清验收欠账。
- 每项任务写明：预期结果、验收标准、来源文档、依赖、优先级、所属里程碑。决策者是负责人；AI 会话与代码链接记录在任务上——AI 永远不是验收人。
- 优先级：P0 阻塞里程碑/发布路径；P1 为当前里程碑所需；P2 可以等。Bug 严重度与优先级分开记录。
- 任务粒度：半天到两天。更大的工作拆成可演示的成果。调研任务设时间盒，必须以一条结论加一个下一步收尾。
- 日期只在有真实外部约束时填写；投入按半天 / 一天 / 两天粗估。

## 角色

| 角色 | 谁 | 负责 |
|---|---|---|
| 决策者 | <human> | 意图、★ 产品决策、验收门、合并、关闭 issue |
| Writer | <agent(s)> | 草稿（意图、契约、清单）、实现、自证 |
| Reviewer | <agent，尽可能与 Writer 不同> | 独立测试、基于证据的审查、裁决草案 |

原则：**决策串行，执行并行。** 架构决策收敛到决策者；Writer/Reviewer 只执行，永不单方面重新定义接口或架构。

协作规则：一个 issue 同一时间只指派给一个 agent，开工前先认领；一个 issue、一个分支；目录所有权按 `AGENTS.md`；跨 agent 协作开始前先定契约；只有决策者能合并。

## 第一轮工作（基线轮）

1. 冻结范围来源；消解规划文档之间的冲突；记录以哪份文档为准。
2. 盘点现有代码/资产：可复用 / 需验证 / 重写 / 未实现——每项都要有证据。
3. 写出第一条真实流程的验收脚本：输入、参与者、输出、失败分支（failure branches）。
4. 审计外部依赖（账号、签名、服务、供应商）；列出缺口及其处理顺序。
5. 把第一条流程拆成半天到两天的任务，并排好下一轮队列。

## 完成标准

合并 ≠ 完成。一项任务的完成须同时满足：验收标准达成、证据（构建/版本、测试结果、截图或决策记录）已附上、决策者已确认用户可见的结果。涉及授权、重复提交、离线恢复、通知或 AI 写入数据的功能，必须验证相关的 failure 分支。原型、模拟数据和历史测试运行记录都不是验收证据。

## 节奏

- 每日开工（5 分钟）：定下主要成果，检查依赖，然后开工。
- 每日收尾（5 分钟）：更新状态、证据、下一步、实际投入。
- 每周回顾（20 分钟）：演示已完成成果，清除阻塞，选定下周任务，检查范围变更。
- 新想法进储备池；要插入当前轮次，必须说明它替换哪项任务以及影响。

## 任务模板

```text
Goal: 这项任务完成后，用户/项目得到什么结果？
Scope: 具体交付什么？
Acceptance: 可观察、可复现的通过条件。
Source: 产品文档、规格文档、原始编号。
Dependencies: 必须先完成的 issue 或外部条件。
Evidence: 代码变更、构建/版本、测试结果、截图/录屏，或决策记录。
Wrap-up: 实际结果、未完成项、后续任务。
```

Bug 另须写明：复现步骤、预期 vs. 实际、环境/版本、影响范围、修复验证。决策另须写明：备选方案、选择理由、影响、决策日期。
