## 2. 行为用例

用例 ID 格式：`<PREFIX>-<NNN>`（前缀按功能定，如 `AUTH-001`）。每条用例一行/一组，形状如下：

- **<PREFIX>-001 <简短业务名>**
  - Given <前置条件，用业务事实陈述>
  - When <一个业务动作或事件——绝不能是 UI 手势>
  - Then <可观察的业务结果>

书写规则（评审时会查——违反即过不了可映射性检查）：
- ✅ 允许词：submit（提交）、confirm（确认）、receive（接收）、display（展示信息内容）、expire（过期）、reject（拒绝）…
- ❌ 禁用词（实现层）：click、tap、swipe、long-press、toast、modal、dialog、spinner、grayed-out、button、组件名、屏路由、API 路径、像素值、存储细节——即任何只有一个平台或一种实现才说得出口的词。
- 期望结果必须是业务事实（状态变化、数据结果、谁能看到什么），绝不能是呈现细节。
- 三个合法例外：① 纯展示用例——把信息内容写成业务期望，并在末尾附 "(layout per design source)"（布局以设计来源为准）；② 不可观察的内部行为——干脆不要写；③ 真正只属于单个平台的行为——移到 §3 平台差异。
- 拦截/拒绝类用例必须显式断言反面（例如"……且不创建任何 <记录>"、"不调用该 API"）——只断言成功路径提示文案的用例，在坏实现面前也能通过。
- 每条用例在有帮助时在小节注记里标注来源：设计屏 / 契约条款 / 铁律。
